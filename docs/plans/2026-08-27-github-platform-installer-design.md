# GitHub Platform Installer Design

English | [中文](2026-08-27-github-platform-installer-design.zh.md)

## Goal

Publish a private GitHub Packages npm installer that users install with `npm install -g @bhnan/dsh-filetree`; the installer selects a macOS Apple Silicon or Linux x64 runtime carrying the current DeepSeek Harness file-tree changes.

## Architecture

The distribution has one user-facing package and two platform packages:

- `@bhnan/dsh-filetree` exposes the `dsh` command and declares the two platform packages as optional dependencies.
- `@bhnan/dsh-filetree-macos-arm64` declares `os: [darwin]` and `cpu: [arm64]`.
- `@bhnan/dsh-filetree-linux-x64` declares `os: [linux]` and `cpu: [x64]`.

npm installs only the platform package compatible with the host. The entry command resolves that package and delegates to its launcher; unsupported platforms fail with an actionable error.

Each platform package carries the packed DSH, vendored Cordis, and Landlock entry tarballs produced by the existing release packers. Its postinstall step installs those local tarballs into a package-owned runtime directory with npm, allowing the source package names to remain `@deepseek-ai/*` without publishing 228 internal packages under a new scope. The platform launcher executes the installed `@deepseek-ai/dsh` binary from that runtime directory.

The package assembly is generated by a release script from the official build output. It writes the platform manifest, launcher, postinstall script, payload directory, and installation README into a temporary staging directory before `npm pack` creates the platform tarball. The entry package is assembled separately and contains no platform-specific native payload. Installer versions append a private revision to the source DSH version, for example `0.1.1-rc.2-bhn.0.1`, while the embedded DSH payload retains `0.1.1-rc.2`.

## GitHub workflow

`.github/workflows/filetree-package.yml` is manually dispatchable with a `publish` boolean that defaults to false and a `private_version` revision that defaults to `0.1`. A matrix runs on `macos-14` for arm64 and `ubuntu-24.04` for x64. Each job checks out complete history, installs Node 24 and pnpm, runs the official build, packs the DSH/vendor/Landlock inputs, assembles its platform package, installs the resulting package in a clean temporary consumer, and runs `dsh --version` plus a non-network startup smoke.

The workflow uploads both platform tarballs and the entry tarball as artifacts on every dispatch. When `publish` is true, a publishing job uses `GITHUB_TOKEN` with `packages: write` and the `npm.pkg.github.com` registry to publish the three packages. No personal token is stored in the repository, and the workflow never connects to the deployment server.

## Installation and runtime flow

The entry package's bin resolves the installed platform package. The platform postinstall creates its private runtime directory and invokes npm with all bundled tarballs as local file dependencies. External dependencies resolve from npmjs.org; platform optional dependencies remain available to the host platform. A failed local tarball, unsupported platform, or runtime install exits nonzero and leaves no partially advertised executable.

The published package README documents the scoped `.npmrc` mapping and `read:packages` personal access token required by clients. Tokens are supplied through the environment or the user's npm configuration and never appear in package files or workflow logs.

## Verification

The assembly script has unit coverage for package names, version alignment, `os`/`cpu` selectors, payload completeness, and launcher paths. The workflow performs clean packed-install smoke tests on both target runners. The server at `123.56.81.22` is verified separately with read-only commands after publication: Ubuntu 24.04, x86_64, Node 24.19.0, npm 11.17.0, pnpm 11.22.0, and approximately 3.58 GB RAM were observed; the validation must not replace or restart the existing service.
