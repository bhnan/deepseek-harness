# AI Native 软件开发流程 Skill

本 skill 把「AI 辅助下的软件开发生命周期」固化成可执行的流程。核心思想来自 Anthropic 应用 AI 团队
《The AI Native SDLC Playbook》：**写代码已经是最快的一步，瓶颈在上下游协同**，因此要把 AI 嵌入整个
生命周期，把单向流水线改成**循环**，每个阶段交一份**版本化的产物**，供人读、也给 AI 接着执行。

## 0. 三条总原则

1. **循环而非流水线**：Plan → Design → Build → Test → Deploy → Maintain 首尾相接，Maintain 的结论
   写成新的 intent.md 回到 Plan，形成闭环。不要当作一次性线性任务做。
2. **每阶段交付一份版本化产物**：产物进版本控制、可审计、可追溯，下一阶段直接读取上一阶段的产物，
   不做口头交接。产物同时给人看、给 AI 执行。
3. **人在关键节点把关**：AI 负责产出与执行，人在「计划批准、PR 审查、生产发布」等关键节点做判断——
   确认目标是否正确、风险是否可接受、权限是否合理。不要逐行替 AI 检查机械错误。

## 1. 六阶段流程（一个开发要走的完整路径）

### 阶段 1 — Plan（规划）：把需求问清楚

目标：产出 `intent.md`（意图文档）。**这是需求生成的核心阶段，也是本 skill 的重点。**

做法：
- 用**澄清式提问**与提出者对话，不要拿到一句描述就开写。围绕以下维度追问：
  - **问题**：要解决什么真实问题？现状是什么、痛点在哪？
  - **用户**：给谁用？主要用户与次要用户分别是谁？
  - **约束**：技术栈、合规、安全、性能、时间、成本约束有哪些？
  - **成功标准**：怎样算做成？可量化的验收指标是什么（能用测试/指标验证的才算）？
  - **范围/非目标**：明确**哪些不做**（out of scope），防止范围蔓延。
- 需求成立后提交 `intent.md`，内容包括：背景与问题、目标用户、核心需求、约束、成功标准、非目标。
- 需求不成立或信息不足时，**不要直接进入 Design**，继续澄清，直到提出者确认。

### 阶段 2 — Design（设计）：把需求变成方案

目标：产出 `spec.md`（规格文档，即施工图）。

做法：
- 先读取上一阶段的 `intent.md`（本 skill 假定流程内产物已生成；若无，先补 Plan）。
- 再读取项目已有规则资产（见 §2）：品牌/安全/合规/UX 相关的 Skill，保证方案符合组织约定。
- `spec.md` 要写清：功能如何工作、数据如何流动、会改动哪些系统、**必须遵守哪些规则**、
  接口与字段、异常与边界（如超时、权限、第三方依赖失败）。

### 阶段 3 — Build（构建）：计划没批准，先别动代码

目标：产出 `plan.md`（实现计划）+ 代码 + 测试。

做法：
- **先进入计划模式**：只读代码库，列出「要改哪些文件、怎么验证、风险点」，把计划交给用户审阅；
  在计划被接受**之前不写任何实现代码**。计划可反复修改，通过的版本写进 `plan.md`。
- 动手前按需加载 §2 的规则资产（CLAUDE.md / Skill / Hook / Subagent）。
- 复杂任务拆给 Subagent（专职子代理，独立上下文、只拿所需工具），主线程负责分配与汇总。

### 阶段 4 — Test（测试）：别听 AI 说「完成」，让结果作证

目标：产出可验证的测试证据。

做法：
- 自己跑测试、跑构建、比对结果，改到真过为止；交付时附**测试结果与关键证据**（输出/截图），
  只说「已完成」不算数。
- **复核与实现分离**：换一个全新对话做只读复核，避免实现者沿用错误思路检查自己。
- 若项目有 Evals（持续评测）：更换模型、修改规则（CLAUDE.md/Skill/Hook）后，重跑既有任务
  并用同一标准比对结果；不合格就不能进入开发中的项目。线上出过的问题要固化成 Evals，防止回踩。

### 阶段 5 — Deploy（部署）：AI 准备上线，人守最后一关

目标：产出带审查记录的 PR，通过后走 CI/CD。

做法：
- 先做 **PR 审查**：按 REVIEW.md 规定的顺序——先找逻辑错误，再查安全漏洞，然后对照 `spec.md`
  和 `plan.md` 确认功能没有跑偏。审查结论写入 PR 记录。
- 审查通过后交给 CI/CD 流水线：CI 自动构建+测试，CD 把通过版本送到开发/测试/生产环境。
- **按环境分级授权**：开发环境 AI 可自行部署；生产环境只准备发布，**绝不主动上线**。
  真正上线前，若存在 Hook，发布命令会被拦截，直到具名发布负责人授权。

### 阶段 6 — Maintain（维护）：让线上事故回到第一步

目标：产出事故记录，并可能生成新的 `intent.md`，重新进入循环。

做法：
- 监控脚本盯错误率、延迟等指标，越界时 AI 做**只读诊断**（只查不改）。
- 严重时提出修复建议，或触发**事先批准且演练过**的回滚（不临时发明高风险操作）。
- 指标恢复正常后，把处理结论写成事故记录；若暴露了新需求/新问题，生成新的 `intent.md` 回到 Plan。

## 2. 配套规则资产（Build 阶段按需加载/维护）

| 资产 | 作用 | 定位 |
|---|---|---|
| **CLAUDE.md**（项目根目录） | 构建/测试方式、目录职责、哪里不能碰、AI 常犯的错误 | 通用指导，每次开工先读 |
| **Skill**（本项目即为此类） | 某「一类活」的复用规范（如"对外接口必须先验证身份"） | 比 CLAUDE.md 更聚焦 |
| **Hook**（按操作触发） | 改受保护文件、碰敏感信息、执行发布命令时自动拦截 | 硬性红线，唯一能"拦下动作"的层 |
| **Subagent** | 专职子代理：独立上下文、只拿所需工具，查代码/验证功能/清理等 | 拆分重复工作，避免对话越做越乱 |

指导规则（CLAUDE.md/Skill）说明"应该怎样做"但无法保证每次都符合；**必须强制执行的红线交给 Hook**。

## 3. 需求生成的提问清单（Plan 阶段速查）

拿到任何需求/开发请求时，先对照这份清单，缺哪项问哪项：

- [ ] **问题**：要解决什么真实问题？现状与痛点？
- [ ] **用户**：给谁用？有无第三方/多角色视角差异？
- [ ] **约束**：技术栈、合规/安全、性能、数据来源、时间与成本？
- [ ] **成功标准**：可量化的验收指标？（"能跑"不算，要有可验证的标准）
- [ ] **非目标**：明确哪些不做？
- [ ] **变更面**：会改动哪些系统/文件/接口？影响面多大？
- [ ] **边界与异常**：超时、权限不足、依赖失败、数据缺失时怎么办？
- [ ] **验证方式**：怎么证明做对了？（测试用例、对比基准、截图/输出）

## 4. 落地顺序（不必一次配齐，缺哪补哪）

- **第 1 层（无前置条件，直接可用）**：intent.md / CLAUDE.md / 测试反馈 / Hook / Plan mode
- **第 2 层（固化成熟做法）**：Skills、Subagents、Evals
- **第 3 层（AI 进入需求设计与审查）**：intent + Skills 支撑需求；规则+检查标准支撑 PR 审查
- **第 4 层（接入 CI/CD）**：前提是先建好 PR 审查与 Hook
- **第 5 层（线上自动回流）**：监控 → AI 只读诊断 → 新 intent.md（追求最高自动化才做）

落地时先找**最耗时、最容易出错**的环节，缺哪项补哪项，不必从第 1 层做到第 5 层。

## 5. 阶段门禁检查清单（每阶段结束前自检）

- **Plan 完**：intent.md 是否包含问题/用户/约束/成功标准/非目标，且经提出者确认？
- **Design 完**：spec.md 是否说明功能、数据流、改动系统、必守规则、边界异常？
- **Build 完**：plan.md 是否先于代码被批准？改动是否严格限定在计划内文件？
- **Test 完**：是否附了可验证证据（测试输出/截图）？是否做了独立复核？
- **Deploy 完**：PR 是否按 REVIEW.md 顺序审查并留痕？生产发布是否由具名负责人授权？
- **Maintain 完**：事故是否记录？是否产出/更新了 intent.md 让循环继续？

## 6. 注意事项

- 本流程来自 Anthropic 生态（CLAUDE.md、skills、hooks 等是 Claude 的具体实现），**照搬工具名不必要**；
  吸收的是**流程判断**，落到本仓库时用现有代码托管、CI/CD、测试与权限系统实现。
- 与更具体的项目 skill 冲突时：本项目 skill（如交易看板相关）优先，本 skill 提供的是通用流程骨架。
- 每个阶段产物都应**进入版本控制**，作为可审计的执行轨迹；不要只在对话里"口头确认"。
